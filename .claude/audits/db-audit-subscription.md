# DB Audit -- Subscription Tier State on Plan Change (Upgrade/Downgrade)

Date: 2026-08-05
Scope: Firestore users/{uid}.subscription field correctness across Google Play plan changes (upgrade/downgrade/crossgrade), not initial purchase. Read-only audit, no fixes applied.

Files reviewed: functions/src/subscriptionNotifications.ts, functions/src/googlePlayHelpers.ts, functions/src/verifyPurchase.ts, services/purchaseService.ts, hooks/useSubscription.ts, components/settings/SubscriptionManager.tsx, services/usageService.ts, types.ts, firestore.rules.

---

## HIGH

### H1. Plan-change purchase is never told to replace the old subscription -- Play can create a second concurrent subscription instead of upgrading
services/purchaseService.ts:184-227 (purchaseProduct) calls IAP.store.order(orderTarget) with no oldPurchaseToken/prorationMode/replace parameters. cordova-plugin-purchase's Google Play Offer.order() needs an explicit old-purchase reference to invoke Play Billing's SubscriptionUpdateParams "replace" flow; without it, ordering family_monthly while already subscribed to premium_monthly is just a second independent purchase, not an upgrade. Depending on plugin/Play Console config this either double-charges (two live subscriptions on the same Play account) or Play rejects the order -- neither path is handled or surfaced to the user as a plan-change failure.
SubscriptionManager.tsx:89-148 (handleUpgrade) also never looks up the user's current purchase token before calling purchaseProduct(productId), so there is no way to pass one even if purchaseProduct supported it.
Fix: Track the active purchase_token/product_id (already stored on subscription), pass it through to the plugin's replace API on upgrade/crossgrade, and add a linkedPurchaseToken reconciliation path server-side (H2).
### H2. RTDN handler has no linkedPurchaseToken reconciliation -- old-token and new-token notifications race and can leave the user's tier pointing at the superseded subscription
functions/src/subscriptionNotifications.ts:116-206. On a genuine Play-side plan change, Google sends two independent RTDN messages: one for the old purchaseToken (typically SUBSCRIPTION_CANCELED, type 3) and one for the new purchaseToken (SUBSCRIPTION_PURCHASED, type 4). The handler keys every write purely off whichever purchaseToken is in the message (purchaseTokens/{purchaseToken} lookup at line 131, resolveSubscriptionState(subscriptionId, purchaseToken) at line 182) and unconditionally overwrites the entire users/{uid}.subscription map (lines 183-193) with whatever that single token/product resolves to. There is no linkedPurchaseToken field read anywhere (confirmed absent from googlePlayHelpers.ts and verifyPurchase.ts -- not just unused, never referenced), so nothing correlates the two messages or orders them.
Concrete failure: user upgrades premium to family. Pub/Sub delivers CANCELED for the old premium token and PURCHASED for the new family token with no ordering guarantee (separate messages, independently retried on function cold-start/timeout). If the old-token CANCELED message is processed after the new-token PURCHASED message (a plain race, not a rare edge case -- both fire within the same second), the handler runs the re-verify-with-Play branch (line 178) for the old token, gets back tier=premium, status=cancelled, product_id=<old premium id>, purchase_token=<old token>, and that whole-map update() clobbers the correct family/active state the new-token event had just written. The user is left showing cancelled on a premium product id while actually holding a live, paid family subscription -- useSubscription.ts and usageService.ts both key off exactly this field, so they would immediately clamp the user to free-tier limits despite an active paid subscription.
Fix: On any actionable RTDN, call purchases.subscriptions.get and read linkedPurchaseToken off the response; if present, treat this as a plan-change event and only accept the write if the incoming token is the user's current purchase_token or the linked chain resolves forward to a token newer than what's stored (e.g. compare startTimeMillis/current_period_end, or a monotonic version field), rather than blind last-write-wins.

## MEDIUM

### M1. PRODUCT_TIER_MAP is duplicated with no shared source -- client/server can silently disagree
functions/src/googlePlayHelpers.ts:10-15 and services/purchaseService.ts:34-39 each hand-maintain the same 4-entry product-to-tier map. They currently agree, but nothing enforces that: add a new product SKU (e.g. a promo tier) to the client map and forget the server map (or vice versa) and verifyPurchase.ts:83-86 throws invalid-argument "Unknown product" for a purchase the client just successfully sold, or the RTDN handler's fallback-to-currentSub-tier at subscriptionNotifications.ts:149 silently keeps the user on their prior tier forever for that product. This is exactly the kind of tier-mapping drift most likely to bite when adding a new plan tier rather than at initial 4-product launch.
Fix: Generate both maps from one JSON/constants file checked at build time (or have the client fetch the tier map from a callable/Remote Config instead of hardcoding it), so client and server can't diverge.

### M2. SubscriptionManager client-side optimistic update always fails silently -- real state is fully dependent on CF write timing, not actually optimistic
components/settings/SubscriptionManager.tsx:124-135 writes subscription:{tier, status:'active', ...} via updateSubscription (-> hooks/useSubscription.ts:129-146 -> plain updateDoc) immediately after purchaseProduct() resolves. But firestore.rules:117-125 (subscriptionUnchanged()) rejects every client update that changes the subscription field on users/{userId} -- by design, only verifyPurchase.ts/subscriptionNotifications.ts (Admin SDK) may write it. So this optimistic write always throws permission-denied, which is caught and swallowed (.catch(...) at line 133, log-only). It happens to be harmless today (the real write already landed via verifyPurchase's admin-SDK transaction before purchaseProduct()'s promise resolves -- see purchaseService.ts:136-145), but the code and its comment claiming an instant zero-ms refresh are actively misleading: there is no working optimistic path, the UI only updates once useSubscription.ts's onSnapshot listener (line 49) observes the CF's write. If verifyPurchase is ever slow (cold start, Play API retry backoff up to 3x2s at verifyPurchase.ts:97-101) the success toast fires before Firestore/UI reflects the new tier, and this dead code gives no actual mitigation.
Fix: Either remove the dead client write (rules will never allow it) or replace it with genuine client-local optimistic state (component state, not a Firestore write) that is reconciled/cleared once the listener catches up.

### M3. canAddHouseholdMember limit check skips the active-status clamp getUsageLimits applies -- stale tier during a lapsed/cancelled window over-grants
services/usageService.ts:405-419 computes maxMembers straight from user.subscription?.tier with no status check. Contrast getUsageLimits two dozen lines above it (usageService.ts:132-134), which explicitly clamps to free unless status is active/trialing, with the comment that RTDN-driven Firestore updates can lag and some notification types (CANCELED, ON_HOLD) intentionally leave tier untouched. That is exactly the scenario subscriptionNotifications.ts produces: SUBSCRIPTION_CANCELED/SUBSCRIPTION_ON_HOLD go through the re-verify branch (not IMMEDIATE_DOWNGRADE_TYPES), which sets status to cancelled/past_due but keeps tier at family (still resolved from PRODUCT_TIER_MAP, line 149). During that window (payment failure, grace period, or the CANCELED period before an EXPIRED/REVOKED terminal event finally lands), getUsageLimits correctly clamps the user to free limits, but canAddHouseholdMember still reads tier===family and allows growing the household to 5 members -- members who will then all get clamped down (or worse, inherit stale access per H2) once other checks catch up, and the extra invited slots are not reclaimed anywhere.
Fix: Reuse the same isSubActive gate in canAddHouseholdMember (or centralize effective-tier resolution into one function both call).

## Not an issue (checked, handled correctly)

- Immediate access cutoff on downgrade: SubscriptionManager.tsx:93-105 redirects every downgrade (including to Free) straight to the Play Store subscriptions page rather than calling purchaseProduct/writing Firestore itself -- so there is no client-side path that could prematurely clamp a user to the lower tier before Play's deferred-downgrade billing cycle actually ends. Correct call, though it means a downgrade's actual Firestore tier flip is still fully dependent on H2's unreconciled RTDN race once Play does apply it at renewal.
- Missing Firestore index: no composite queries are involved in subscription reads -- users/{uid} and households/{householdId} are single-document gets throughout useSubscription.ts and usageService.ts. Nothing to index.
- resolveSubscriptionState payment-state mapping (googlePlayHelpers.ts:44-59) correctly treats paymentState 0 (pending/hold) as past_due rather than trusting expiryTimeMillis alone, and verifyPurchase.ts:97-101 retries the propagation-lag case before failing.
